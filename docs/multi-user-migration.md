## 阶段 2:用户空间数据隔离与角色迁移

### 设计原则

- **主数据模式**:业务表(authors / works / edges)增加 `owner_id`(NULL = 公共/策展数据);
  用户空间是私有叶子,公共星云是聚合视图,删除私有数据不影响公共数据。
- **隔离在查询层强制**:所有空间数据接口必须带 owner 上下文,漏配即返回空而非泄露;
  公共接口(/api/graph 等)保持不变、无需登录。
- **角色**:`users.role` 已有 `user` / `admin`;管理接口从单一 `ADMIN_TOKEN` 迁移为
  admin 角色校验,审计 `actor` 记录真实用户。

### 步骤清单(实时状态)

1. Schema v9:业务表加 `owner_id` + 索引,贡献表加归属 ✅
2. 数据层:行级 CRUD 支持 owner 上下文、级联删除/恢复按 owner 约束、
   读缓存按「DB 路径 + 空间」分键、任何空间写入都失效缓存 ✅
3. 后端 API:个人空间 `/api/me/*`(图/搜索/详情/扩散/路径 + 行级 CRUD),
   公开接口保持全局;公共星云 = admin 空间(未认领历史行也视为公共) ✅
4. 贡献归属:登录用户提交自动带 `user_id`,未登录匿名;列表带 `user_email` ✅
5. 角色迁移:移除 ADMIN_TOKEN/HTTPBearer;`require_admin` 角色依赖;
   `ADMIN_BOOTSTRAP_EMAIL` 注册自动提权 + 启动时补角色 + 认领未归属数据 ✅
6. 前端:登录后「我的星云」入口 + 空间切换(公共/我的,API 按空间前缀)、
   数据管理按 admin 角色显隐、移除令牌授权框 ✅
7. 测试与文档:隔离测试(越权 404/403、跨空间引用拒绝、公共/私有互不可见)✅
   README / .env.example / deploy / data_schema / to-do 更新 ✅

### 已确认决策(2026-08-22)

- **Q1 个人空间初始状态**:空空间——用户从零搭建自己的星云。
- **Q2 可见性**:默认仅自己可见(私有);公开/发布机制留到聚合层阶段。
- **Q3 首个管理员**:`.env` 配置 `ADMIN_BOOTSTRAP_EMAIL`,该邮箱注册自动提权为
  `admin` 角色;启动时若该邮箱已存在则自动补齐角色。
- **Q4 ADMIN_TOKEN**:彻底移除——管理接口只接受 admin 角色登录态;前端管理入口
  由登录用户角色驱动,删除令牌授权框与 adminAuth 模块。
- **现有数据归属**:当前全部策展数据(authors/works/edges)认领为
  `ADMIN_BOOTSTRAP_EMAIL` 用户的个人空间;**公共星云 = admin 的空间**,
  未登录游客仍可浏览(owner_id 为空的历史行在认领前也视为公共)。
- **贡献归属**:登录用户提交「点亮星空」自动带 `user_id`;未登录仍可匿名提交。
- **前端空间切换**:左侧栏「公共星云 / 我的星云」切换;我的星云需登录。
- **数据表结构(2026-08-22 补充)**:保持单表 + owner_id,不拆两套表;
  新增 `users.space_visibility`(默认 `public`),星际跃迁只读公开星云。
- **用户数据 → 公共星云(2026-08-22 补充)**:后台流程(AI 预审 + 人工确认),
  用户无需手动提交;公共星云不收录用户隐私数据——书籍关联/信息是客观事实,
  收录时只取客观字段,必要时内部保留溯源(source_user_id/source_row_id),
  对外 API 不暴露。
